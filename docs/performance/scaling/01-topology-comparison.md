# 동일 총 자원 스케일업·스케일아웃 비교

## 테스트 목적

총 애플리케이션 자원을 4 vCPU·16 GiB, Kafka를 8 partitions·8 consumers로 고정하고 한 VM에 배치한 경우와 두 VM으로 나눈 경우를 비교한다. HTTP load balancer가 없는 실험 환경이므로 Kafka consumer group으로 입력을 분산한다.

## 테스트 조건

| 항목 | 스케일업 | 스케일아웃 |
| --- | --- | --- |
| payment-service | 1×4 vCPU·16 GiB | 2×2 vCPU·8 GiB |
| 전체 consumers | 8개 | 인스턴스당 4개, 총 8개 |
| 입력·PG | 300 EPS·60초, 성공 100% | 동일 |

## 측정 결과

| 지표 | 1×4 vCPU | 2×2 vCPU | 변화 |
| --- | ---: | ---: | ---: |
| 결제 유효 처리량 | 244.838 EPS | 186.662 EPS | -23.8% |
| 입력 추종률 | 81.612% | 62.223% | -19.389%p |
| peak 관측 lag | 3,270건 | 6,993건 | +113.9% |
| 마지막 `PAID` | 종료 후 13.069초 | 종료 후 36.436초 | +23.367초 |
| listener 평균 | 32.588ms | 45.381ms | +39.3% |
| Outbox 처리량 | 17.026 EPS | 17.842 EPS | 유사 |
| 최종 lag·DLT·중복 | 0건 | 0건 | 동일 |

## 결과 해석

스케일아웃 구성도 18,001건을 중복·DLT 없이 처리했다. 다만 같은 8개 처리 슬롯에서 listener 점유시간이 32.588→45.381ms로 늘어 처리량이 낮아졌다. 작은 JVM 두 대의 고정 비용, 인스턴스별 pool·scheduler 중복과 공유 PG·DB 경합은 후보로만 남겼다. 이번 측정에서는 12.8ms 증가분을 구간별로 분리하지 못했다.

이 구성에서는 같은 총 자원의 처리량만 비교하면 1×4 vCPU가 유리했다. 스케일아웃은 다음 테스트에서 한 대가 이탈한 N-1 처리와 최종 정합성을 기준으로 평가했다.
