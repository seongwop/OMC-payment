# 2 vCPU Kafka 소비 병렬성 조율

## 테스트 목적

단일 2 vCPU payment-service에서 partition과 consumer를 함께 늘리며 처리량·lag 변화와 CPU 한계를 확인한다.

## 테스트 조건

- payment-service 1대, 2 vCPU·8 GiB
- WireMock 승인 성공 100%, 본 측정 60초
- partition 수와 listener concurrency를 같은 값으로 변경
- 재기동 후 보정 부하를 거친 실행을 대표값으로 사용

## 측정 결과

### 100 EPS

| Kafka 설정 | 결제 처리량 | peak lag | app VM CPU 최대 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 1/1 | 30.74 EPS | 4,237건 | 비포화 | 직렬 처리 기준선 |
| 3/3 | 66.47 EPS | 2,492건 | 95.98% | 처리량 2.16배, CPU 포화 |
| 4/4 | 79.78 EPS | 1,263건 | 96.57% | 추가 처리량 +20.0% |

### 200 EPS

| Kafka 설정 | 결제 처리량 | peak lag | 종료 후 마지막 `PAID` | listener 평균 |
| --- | ---: | ---: | ---: | ---: |
| 4/4 | 135.629 EPS | 3,780건 | 28.032초 | 30.169ms |
| 6/6 | 163.696 EPS | 2,260건 | 12.864초 | 36.416ms |
| 8/8 | 195.133 EPS | 191건 | 1.502초 | 36.868ms |
| 10/10 | 199.760 EPS | 129건 | 종료 전 완료 | 31.482ms |

4→8 consumers에서는 처리량과 lag이 함께 개선됐다. 8→10의 처리량 증가는 2.37%였고, 10/10에서 200 EPS 입력을 모두 따라갔다.

### 300 EPS

| Kafka 설정 | 결제 처리량 | 입력 추종률 | peak lag | listener 평균 | app VM CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10/10 | 251.332 EPS | 83.781% | 2,554건 | 39.000ms | 79.7% |
| 12/12 | 253.965 EPS | 84.655% | 2,922건 | 47.011ms | 79.24% |
| 16/16 | 275.807 EPS | 91.936% | 1,026건 | 55.751ms | 92.16% |

## 결과 해석

200 EPS에서는 10/10부터 입력률이 처리량 상한이 됐다. 현재 설정의 한계를 보기 위해 입력을 300 EPS로 올렸고, 16/16에서 275.807 EPS까지 증가했지만 app CPU는 92.16%에 도달했다. 12/12→16/16 구간에서 처리량은 8.6% 늘고 listener 시간은 18.6% 길어져 선형 확장은 멈췄다.
