# 정상 API 부하 단계 측정

## 테스트 목적

정상 승인만 발생하는 단일 `e2-standard-2`에서 100 RPS부터 부하를 올리며 안정 구간과 비선형 포화 전환점을 찾는다.

## 테스트 조건

- payment-service 1대, 2 vCPU·8 GiB
- WireMock 승인 성공 100%, 본 측정 60초
- HttpClient pool 170, Bulkhead 160, Hikari 30
- 각 실행 전 워밍업·냉각과 데이터 초기화

## 측정 결과

| 목표 입력 | 실제 실행 | 완료 처리량 | p95 | dropped | 판정 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 100 RPS | 6,001건 | 99.81 RPS | 34.76ms | 0건 | 안정 |
| 150 RPS | 9,001건 | 149.70 RPS | 39.09ms | 0건 | 안정 |
| 200 RPS | 12,001건 | 199.61 RPS | 58.95ms | 0건 | 안정 상한 |
| 250 RPS | 14,908건 | 247.95 RPS | 1,018.48ms | 93건 | 포화 진입 |
| 300 RPS | 10,400건 | 165.95 RPS | 4,384.79ms | 7,600건 | 포화 |

## 결과 해석

200→250 RPS에서 입력은 25% 증가했지만 p95는 17.3배 증가했다. 300 RPS에서는 최대 600 VU가 모두 점유돼 7,600건이 시작되지 못했다. 단일 인스턴스의 포화 전환 구간은 200~250 RPS였다.

실행된 요청은 모두 `PAID`, Outbox `PUBLISHED`에 도달했다. dropped는 결제 실패가 아니라 k6가 목표 arrival를 시작하지 못한 건으로 분리했다.
